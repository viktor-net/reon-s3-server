# AGENTS.md — координация AI-агентов в reon-s3-server

> Версия: 1.0. Дата: 2026-11-01.
> Это канонический файл для AI-агентов. OpenCode автоматически подхватывает
> `AGENTS.md`; если в проекте появится `AGENT.md`, он считается черновиком,
> а истина — здесь.

## 0. Приоритет правил

При конфликте действует такой порядок:

1. **Код, тесты и фактическое поведение сервиса** — источник истины.
2. **`CONTRIBUTIONS.md`** — формат коммитов, язык, окончания строк.
3. **`README.md`** — продуктовое описание и контракты API.
4. **`AGENTS.md`** — процесс работы агентов.

Если агент не уверен, какое правило применить, он **останавливается и задаёт
вопрос**, а не выбирает удобный вариант. Молчаливое «я предположил» запрещено.

## 1. Глоссарий

| Термин | Значение |
|---|---|
| **Агент** | AI-модель в сессии OpenCode, включая суб-агентов. |
| **Воркер** | Фоновый сервис приложения (`ReconciliationBackgroundService`, `RetentionBackgroundService` и т. п.). Это **не** AI-агент. |
| **Сессия** | Один диалог OpenCode со своим контекстом и выбранной моделью. |
| **Экземпляр** | Отдельный процесс/клиент OpenCode: другая машина, другой терминал, другой worktree. |
| **Оркестратор / scribe** | Роль: формулирует задачу, ведёт доску, назначает исполнителей, делает reduce, пишет README. |
| **Исполнитель (executor)** | Роль: пишет код и тесты по узкому ТЗ. |
| **Explorer** | Роль: только читает и ищет, ничего не меняет. |
| **Reviewer** | Роль: независимо проверяет diff, ничего не правит. |
| **Map** | Фаза: разбить задачу на независимые части и выполнить их. |
| **Reduce** | Фаза: свести результаты map в одно решение, разрешить противоречия. |
| **Brief** | Письменное ТЗ задачи: цель, не-цели, ограничения, файлы, критерии приёмки. |
| **Доска** | Каталог `.agents/tasks/<task-id>/` в репозитории. |
| **Lease** | Временное право сессии владеть задачей; истекает, если нет heartbeat. |
| **Worktree** | Отдельная рабочая копия репозитория для параллельной версии. |

**Важно:** в этом проекте слово «агент» никогда не означает фоновый воркер.
Если речь о воркере — пишем «воркер» или «background service».

## 2. Роли и ответственность

| Роль | Что делает | Что не делает |
|---|---|---|
| **Оркестратор / scribe** | Пишет `brief.md`, назначает агентов, ведёт `state.json`, обновляет `README.md` и `docs/`, делает reduce | Не пишет код в `src/` и `tests/`; не ревьюит сам себя |
| **Explorer** | Ищет файлы, читает код, собирает факты, приносит ссылки на строки | Не меняет файлы |
| **Executor** | Пишет код и тесты строго в границах brief | Не трогает `README.md`, `docs/`, `AGENTS.md`; не расширяет скоуп |
| **Reviewer** | Проверяет diff, тесты, граничные случаи, соответствие brief | Не правит код; не подписывает свою же работу |
| **Asset-агент (image)** | Генерирует изображения по промпту | Не участвует в текстовом map/reduce |
| **Modeler-3D** | Зарезервированная роль для 3D-моделей | Пока не настроен, см. §13 |

Правило разделения: **автор не проверяет свою работу**. Если reviewer недоступен,
это фиксируется в `reduce.md` как риск, а не игнорируется.

## 3. Модели и fallback

Основной канал — **OpenCode Go**, резерв — **OpenCode Console (Zen)**.
Модель в чате может быть любой: пользователь вправе начать диалог с любой
моделью, но роли ниже фиксируют, кто что делает.

| Роль | Go (primary) | Zen (fallback) | Зачем |
|---|---|---|---|
| Оркестратор / scribe | `opencode-go/qwen3.8-max` | `opencode/qwen3.8-max` | Формулировка задачи, dispatch, reduce, README |
| Executor | `opencode-go/deepseek-v4.1-flash` | `opencode/deepseek-v4.1-flash` | Код и тесты |
| Explorer | `opencode-go/deepseek-v4.1-flash` | `opencode/deepseek-v4.1-flash` | Дешёвый поиск и чтение |
| Reviewer | `opencode-go/kimi-k3.1-pro` | `opencode/claude-sonnet-5-5` | Независимая проверка |
| Image | любая доступная image-модель | — | `experimental_image_generate` |
| 3D | TBD через MCP/plugin | — | См. §13 |

Правила:

- Fallback — это **осознанное переключение**, а не автоматическая магия: при
  исчерпании лимитов Go сессия явно переходит на Zen и фиксирует это в
  `journal.ndjson`.
- Не хранить ключи и токены в `.agents/`, `AGENTS.md` и коммитах.
- Дешёвая модель допустима для map, но **не для финального reduce**: reduce
  закрепляет ошибки в результате.
- Модель не выбирает себе роль сама. Роль задаётся brief и конфигом агента.

## 4. Маршрутизация задач

Роутинг детерминированный, без отдельной LLM-модели-диспетчера. Диспетчер
ошибается, стоит денег и добавляет задержку; команда и brief надёжнее.

| Размер | Признаки | Кто работает |
|---|---|---|
| **S** | 1 файл, 1 очевидная правка, нет миграций и S3 | Executor напрямую, без суб-агентов |
| **M** | 2–5 файлов, есть тесты | Оркестратор + 1 executor + reviewer |
| **L** | Несколько модулей, миграции, параллельные версии | Оркестратор + 2–4 исполнителя + reviewer + reduce |

Команды (если настроены в `.opencode/commands/`):

- `/quick` — S, модель executor, без суб-агентов;
- `/feature` — M/L, оркестратор + воркеры;
- `/deep` — L с усиленным reduce;
- `/readme` — только scribe и только документация.

Если команда не настроена, оркестратор сам классифицирует задачу и записывает
размер в `brief.md` (`size: S|M|L`).

## 5. Жизненный цикл задачи

```
intake → brief → claim → map → verify → reduce → close
```

| Шаг | Владелец | Артефакт | Гейт |
|---|---|---|---|
| **intake** | Оркестратор | запись в `journal.ndjson` | задача понятна, есть task-id |
| **brief** | Оркестратор | `brief.md` | цель, не-цели, файлы, критерии |
| **claim** | Любая сессия | `state.json` + lease | атомарный захват, нет чужого lease |
| **map** | Executor/explorer | `results/<agent>-<attempt>.md` | каждый результат самодостаточен |
| **verify** | Executor + reviewer | вывод сборки/тестов | `dotnet build` и `dotnet test` зелёные |
| **reduce** | Оркестратор | `reduce.md` | противоречия разрешены, риск зафиксирован |
| **close** | Оркестратор | `state.json` = `done` | коммит/PR, журнал закрыт |

Задача не считается выполненной, пока не заполнен `reduce.md` и не пройдены
тесты. «Я проверил глазами» — не гейт.

### 5.1. Передача задачи (handoff)

| От → К | Что передаётся | Как |
|---|---|---|
| Пользователь → scribe | запрос | чат |
| scribe → executor | `brief.md` + `state.json` | суб-агент с полным brief |
| executor → scribe | `results/<agent>-<attempt>.md` | файл + уведомление |
| scribe → executor (S) | задача без планирования | `brief.md` + `size: S` |
| scribe → пользователь | `reduce.md`, вопрос, `blocked` | чат + журнал |
| Go → Zen | та же задача, тот же attempt | `model-fallback` в журнале |

«Вернуть задачу исполнителю» означает: scribe передаёт её DeepSeek flash, если
задача сводится к исполнению. Brief и reduce при этом остаются за scribe; если
scribe недоступен совсем, это фиксируется как риск, а не подменяется молча.

## 6. Доска задач

```
.agents/
├── README.md                  # быстрый старт по доске
├── registry.md                # роли, модели, fallback
├── templates/
│   ├── brief.md
│   ├── state.json
│   ├── result.md
│   ├── reduce.md
│   └── journal-event.json
├── tasks/
│   └── <task-id>/
│       ├── brief.md           # ТЗ, после claim не редактируется
│       ├── state.json         # владелец, lease, статус, файлы
│       ├── journal.ndjson     # append-only события
│       ├── results/
│       │   └── <agent>-<attempt>.md
│       ├── artifacts/         # изображения, 3D, большие выгрузки
│       └── reduce.md          # итоговое решение
├── locks/                     # локальные lock-файлы, не коммитятся
└── journal/                   # общий журнал, если нужен вне задачи
```

Правила:

- `<task-id>` — стабильный ID: `REON-123`, `IR-329` или `local-20261101-01`.
- `brief.md` после claim **иммутабелен**. Изменение — только `brief.v2.md`
  с записью в журнале и повторным claim.
- `state.json` пишет только текущий владелец lease.
- `journal.ndjson` — только append, по одной JSON-строке на событие.
- `results/` — только добавление; перезапись запрещена, новая попытка —
  новый `attempt`.
- `reduce.md` — единственный файл, который читают при закрытии задачи.

## 7. Синхронизация внутри одной сессии

1. **Один оркестратор — один писатель brief.** Суб-агенты не переписывают ТЗ.
2. **Суб-агент не видит контекст родителя.** В промпт передаётся полный brief,
   список файлов, критерии приёмки и запреты. «Сделай как обсуждали» запрещено.
3. **Партиционирование по файлам.** Два исполнителя не пишут в один файл
   одновременно. Пересечение — только через оркестратора.
4. **Map-результаты пишутся в файлы**, а не остаются в чате: это переживает
   compaction и доступно другим сессиям.
5. **Один reducer.** Не «каждый сделал вывод», а один `reduce.md`.
6. **Фоновые суб-агенты**: сохранять `sessionID`, не опрашивать в цикле,
   дождаться уведомления. Продолжение — по `sessionID`, а не новым запуском.
7. **Лимит шагов.** У каждого агента задан `steps`; при исчерпании — вернуть
   промежуточный результат, а не молча продолжать.
8. **Стоп-условия.** Если нужно выйти за границы brief, агент останавливается и
   пишет вопрос в `journal.ndjson` / `results/`.
9. **Reviewer — отдельный и read-only.** Автор не ревьюит себя.
10. **Контекст — не общая память.** Всё, что важно, фиксируется в файлах доски.

## 8. Синхронизация между сессиями и экземплярами

Основной транспорт — **git + worktree + файловая доска**. Отдельная БД для
старта не нужна: git уже даёт атомарность, историю и работу с разных машин.

### 8.1. Ветки и worktree

- Одна задача — одна ветка: `agent/<task-id>`.
- Один исполнитель — один worktree: `.worktrees/<task-id>-<agent>` (путь
  настраивается через `worktree.directory`, каталог не коммитится).
- Параллельные версии одной задачи — отдельные ветки
  `agent/<task-id>/v1`, `agent/<task-id>/v2`; сравниваются в reduce.
- Merge — только через PR/ревью; force-push в общие ветки запрещён.

### 8.2. Claim и lease

Claim — атомарный захват задачи:

1. Прочитать `state.json`.
2. Если `lease_until` в будущем и владелец не я — задача занята, выбрать другую.
3. Если lease истёк — разрешён reclaim с записью причины в журнал.
4. Создать/обновить `state.json` и **запушить** изменение; если push отклонён,
   перечитать и повторить с шага 1.

Локально тот же захват делается атомарным созданием файла
(`CreateNew` / `noclobber`), чтобы два терминала на одной машине не начали
одну задачу одновременно.

Поля lease:

```json
{
  "taskId": "REON-123",
  "status": "claimed",
  "ownerSession": "ses_...",
  "ownerModel": "opencode-go/qwen3.8-max",
  "branch": "agent/REON-123",
  "worktree": ".worktrees/REON-123-orchestrator",
  "files": ["src/Reon.Core/Services/MultipartUploadService.cs"],
  "leaseUntil": "2026-11-01T12:30:00+00:00",
  "heartbeatAt": "2026-11-01T12:00:00+00:00",
  "attempt": 1
}
```

- TTL lease — 30 минут; heartbeat — каждые 10 минут.
- Просроченный lease не удаляется сам: reclaim фиксируется в журнале.
- Сессия, потерявшая lease, **немедленно прекращает запись** и отдаёт результаты.

### 8.3. Журнал

`journal.ndjson` — append-only, merge-friendly:

```json
{"at":"2026-11-01T12:00:00Z","event":"claim","task":"REON-123","session":"ses_...","model":"opencode-go/qwen3.8-max","attempt":1}
{"at":"2026-11-01T12:10:00Z","event":"heartbeat","task":"REON-123","session":"ses_..."}
{"at":"2026-11-01T12:20:00Z","event":"result","task":"REON-123","agent":"executor","attempt":1,"path":"results/executor-1.md"}
{"at":"2026-11-01T12:30:00Z","event":"release","task":"REON-123","session":"ses_..."}
```

События не редактируются. Ошибка исправляется новым событием.

### 8.4. Когда нужна БД

Файлы и git достаточны, пока сессий немного и все работают с репозиторием.
PostgreSQL имеет смысл, если:

- больше ~10 одновременных сессий;
- нужны sub-second lease и очередь;
- агенты работают без доступа к git;
- нужен дашборд и история вне git.

Тогда — отдельная БД/схема, **не** база приложения `reon`. Схема и запросы —
в `docs/agents/postgres-board.sql`. SQLite по сетевой папке не использовать:
блокировки файла ненадёжны.

## 9. Параллельные версии

- Каждая версия — отдельная ветка и worktree.
- Версии не мержатся автоматически; оркестратор сравнивает их в `reduce.md`.
- В `results/` версия указывается в имени: `executor-1-v2.md`.
- Победившая версия проходит verify и merge; проигравшие остаются в истории.
- Нельзя держать две версии в одном worktree: это гарантированный конфликт.
- Общие файлы (`README.md`, `docs/`, `AGENTS.md`) правит только scribe, после
  reduce. Исполнители предлагают изменения текстом в `results/`.

## 10. README.md и документация

- `README.md` — общий артефакт, а не место экспериментов.
- Единственный писатель — **scribe/оркестратор**.
- Executor может предложить формулировку в `results/<agent>.md`; применяет её
  scribe после reduce.
- Изменения API, эндпоинтов, статусов и конфигов обязаны попасть в `README.md`
  и, если нужно, в `docs/`.
- Проверять ссылки, примеры curl и таблицы эндпоинтов; не оставлять
  «TODO» и «см. позже».

## 11. Приёмка и definition of done

Минимальный гейт для любой задачи с кодом:

```bash
dotnet build
dotnet test
```

Если менялись миграции:

```bash
dotnet ef database update \
  --project src/Reon.Infrastructure \
  --startup-project src/Reon.Api
```

Если менялся стенд или Docker:

```bash
bash scripts/check-stand.sh        # Windows: pwsh -File scripts/check-stand.ps1
docker compose up -d --build
```

Definition of done:

- [ ] `brief.md` заполнен и не менялся после claim.
- [ ] Изменения не выходят за список файлов (или расширение согласовано).
- [ ] `dotnet build` и `dotnet test` зелёные; вывод приложен в result.
- [ ] Reviewer проверил diff и граничные случаи.
- [ ] `reduce.md` заполнен; риски и открытые вопросы перечислены.
- [ ] Коммит оформлен по `CONTRIBUTIONS.md` (русский, повелительное наклонение,
      `[TASK-ID]`).
- [ ] В `journal.ndjson` есть `claim`, `result`, `release`/`close`.

Запрещено писать «тесты не запускал, но должно работать». Либо запуск, либо
явный риск в `reduce.md`.

Как убедиться, что сами агенты (Qwen, DeepSeek) работают как ожидается, —
`docs/agents/verification.md`: discovery, проверка фактической модели,
негативные тесты прав, canary-задачи, lease и fallback.

## 12. Безопасность

- Не коммитить секреты, пароли, токены, `X-Reon-Actor` с реальными данными.
- Не давать агентам доступ к production Postgres/S3; локальный стенд — только
  из `.env.example`.
- Не выполнять разрушительные операции (`DROP`, `DELETE` без `WHERE`,
  `docker compose down -v`, force-push) без явного разрешения человека.
- Reviewer и explorer — read-only по файлам.
- Любая операция с внешними эффектами (миграции, удаление объектов S3)
  фиксируется в журнале и требует подтверждения.

## 13. Изображения и 3D (зарезервировано)

### 13.1. Изображения

- Инструмент: `experimental_image_generate` (доступен, когда подключена
  image-модель).
- Это не чат-модель: она не вызывает инструменты и не участвует в map/reduce.
- Результат сохраняется в `.agents/tasks/<task-id>/artifacts/` или в
  `assets/`; путь и модель фиксируются в sidecar-JSON.
- Промпт, модель, seed (если есть) и хеш файла — обязательны для
  воспроизводимости.
- Ассеты проходят human review; автоматически в прод не попадают.

### 13.2. 3D-модели

- В OpenCode V2 нет встроенного 3D-инструмента. Роль `modeler-3d`
  зарезервирована; реализация — через MCP-сервер или плагин, который
  предоставит инструмент `3d_generate`.
- Контракт будущего инструмента:

```json
{
  "prompt": "string",
  "format": "glb|gltf|obj|fbx",
  "outputPath": ".agents/tasks/<task-id>/artifacts/model.glb",
  "references": ["optional/path.png"]
}
```

- До появления инструмента агенты **не симулируют** генерацию 3D и не пишут
  бинарные файлы вручную. Вместо этого — комментарий в `reduce.md`:
  «3D-ассет не сгенерирован: инструмент отсутствует».

## 14. Сбои и конфликты

| Ситуация | Действие |
|---|---|
| Два claim на одну задачу | Побеждает тот, чей push/атомарное создание прошло; проигравший перечитывает state и выбирает другую задачу |
| Истёк lease | Reclaim с записью причины; старый владелец прекращает запись |
| Сессия упала | Lease истекает; результаты, уже записанные в `results/`, сохраняются |
| Тесты упали | Задача не закрывается; результат с выводом, reviewer фиксирует причину |
| Конфликт файлов | Оркестратор разводит по worktree; никакого last-write-wins |
| Лимиты Go кончились | Явный переход на Zen, запись в журнал, продолжение с того же артефакта |
| Модель вернула неполный результат | Новый attempt, старый результат не перезаписывается |
| Нужно выйти за скоуп | Стоп, вопрос человеку/оркестратору, запись в журнал |

## Приложение C. Принципы, которые мы зафиксировали

1. **Агент ≠ воркер.** Не смешивать AI-агентов и background services.
2. **Роль важнее модели.** Сначала роль и границы, потом выбор модели.
3. **Конфиг — это guardrails, модель — runtime.** Конфиг задаёт, что возможно;
   модель решает, что произойдёт.
4. **Детерминированный роутинг лучше LLM-диспетчера.** Команды и brief
   предсказуемее, чем ещё одна модель, угадывающая сложность.
5. **Один оркестратор — один reducer.** Не «каждый сделал вывод».
6. **Map-результаты — в файлы.** Контекст не общая память.
7. **Партиционирование по файлам и worktree.** Параллельные писатели в один
   файл — это конфликт, а не параллелизм.
8. **Lease вместо «кто первый начал».** Просроченный lease возвращается явно.
9. **Тесты — объективный reducer.** «Я проверил» не считается.
10. **Автор не ревьюит себя.** Reviewer — отдельный и read-only.
11. **На reduce не экономят.** Дешёвая модель на map допустима, на reduce — нет.
12. **Не выходить за скоуп молча.** Стоп, вопрос, запись в журнал.
