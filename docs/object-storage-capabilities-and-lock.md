# Возможности провайдера и защита от удаления (Object Lock)

Документ фиксирует решение по двум связанным дефектам UI:

- интерфейс показывает действия (Lifecycle, теги, режим доступа, Object Lock),
  которые текущий S3-провайдер не поддерживает;
- Object Lock «включается» при создании бакета, но фактически не работает.

Решение опирается на PostgreSQL: сервис хранит реестр возможностей провайдера
и собственную защиту от удаления для провайдеров без S3 Object Lock.

## 1. Проблема

S3-совместимые провайдеры поддерживают разные подмножества функций. Текущий
провайдер — Swift s3api:

| Возможность | Swift s3api | Следствие |
|---|---|---|
| Versioning | только при включённом object versioning в кластере | запись может вернуть 501 |
| Object tags | не поддерживает | `PUT .../tags` → 501 |
| Lifecycle | не реализован | `PUT .../lifecycle` → 501 |
| Bucket policy | не поддерживает | `PUT .../access` → 501 |
| Object Lock | заголовок принимает, конфигурацию не сохраняет | `security.objectLockEnabled` всегда false |

UI не знает этих ограничений и предлагает рабочие на вид кнопки. Пользователь
заполняет форму, получает 501 и теряет доверие к интерфейсу.

Отдельная проблема — Object Lock. Это механизм самого S3: он запрещает удалять
объекты/версии раньше срока. PostgreSQL не может заставить Swift применять
такую блокировку. Если провайдер её не сохраняет, «включить» S3 Object Lock
нельзя. Можно только:

1. честно отказывать в создании бакета с Object Lock;
2. создавать бакет без блокировки и честно показывать статус;
3. реализовать собственную защиту от удаления на уровне сервиса.

Выбран вариант 3 с честной маркировкой в UI: для провайдеров без S3 Object Lock
сервис включает **защиту от удаления на уровне сервиса**. Это не S3 Object Lock,
но она реально запрещает удаление через API и хранит состояние в PostgreSQL.

## 2. Решение 1: реестр возможностей провайдера

### 2.1. Модель данных

Новая таблица `storage_capabilities`:

```sql
CREATE TABLE storage_capabilities (
    name        varchar(64) PRIMARY KEY,
    supported   boolean     NOT NULL,
    source      varchar(16) NOT NULL, -- config | learned | default
    details     text        NULL,
    updated_at  timestamptz NOT NULL
);
```

Канонические имена возможностей:

| Имя | Что означает |
|---|---|
| `versioning` | включение и приостановка версионирования бакета |
| `object-tags` | чтение и запись S3-тегов объекта |
| `lifecycle` | чтение и запись lifecycle-правил |
| `bucket-policy` | чтение и запись bucket policy (публичный доступ) |
| `object-lock` | S3 Object Lock, а не сервисная защита |

Запись одна на возможность: возможности принадлежат провайдеру, а не бакету.
Если в будущем появится несколько провайдеров, в таблицу добавляется ключ
провайдера; текущая версия рассчитана на один S3-эндпоинт.

### 2.2. Источники значений и приоритет

1. **Конфиг** (`S3:Capabilities:*`). При старте сервис заполняет таблицу, если
   она пуста или если значение в конфиге явно задано. Это базовый срез для
   текущего провайдера.
2. **Обучение по 501**. Если реальная операция вернула
   `StorageCapabilityNotSupportedException`, сервис записывает
   `supported = false`, `source = learned`. Следующий запрос UI уже не покажет
   действие.
3. **Ручное изменение** через API/БД (на будущее). Значение с
   `source = default` перезаписывается конфигом, `learned` — нет, пока
   администратор явно не сбросит.

Runtime-пробы при старте не используются как основной механизм: не все
операции можно безопасно проверить (теги требуют объект, Object Lock отвечает
404 и когда не настроен, и когда не поддерживается). Конфиг + обучение по
фактической ошибке дают предсказуемый результат без лишних запросов.

### 2.3. API

`GET /api/admin/capabilities`:

```json
{
  "provider": "s3",
  "versioning": true,
  "objectTags": false,
  "lifecycle": false,
  "bucketPolicy": false,
  "objectLock": false,
  "maxFileSizeBytes": 1073741824,
  "updatedAt": "2026-11-03T12:00:00Z"
}
```

Поле `maxFileSizeBytes` берётся из `FileStorage:MaxFileSizeBytes` и нужно UI,
чтобы проверить размер файла до загрузки и показать лимит.

### 2.4. Обучение по 501

`StorageCapabilityNotSupportedException` получает канонический ключ
возможности (`versioning`, `object-tags`, `lifecycle`, `bucket-policy`,
`object-lock`). `StorageAdminService` в обработчиках ошибок вызывает
`IStorageCapabilityStore.MarkUnsupportedAsync(key, details)`.

Правило: ошибка 501 не отменяет уже выполненные операции, но фиксирует
ограничение провайдера. Если операция была частью создания бакета, бакет
откатывается (см. раздел 3).

### 2.5. Контракт для UI

- `objectTags = false` → скрыть «Редактировать теги» в карточке объекта.
- `lifecycle = false` → скрыть «+ Добавить правило» и действия редактирования,
  показать пояснение «Провайдер не поддерживает Lifecycle».
- `bucketPolicy = false` → скрыть форму смены режима доступа, оставить
  отображение текущего режима и пояснение.
- `versioning = false` → скрыть переключатель версионирования.
- `objectLock = false` → не скрывать Object Lock, а переключить его на
  сервисную защиту (раздел 3) и явно подписать это в UI.

Если запрос возможностей не удался, UI считает все возможности доступными и
полагается на обработку 501. Это лучше, чем спрятать рабочие функции из-за
сетевой ошибки.

## 3. Решение 2: защита от удаления на уровне сервиса

### 3.1. Что защищаем

Сервисная защита запрещает через API:

- удаление объекта;
- удаление конкретной версии;
- удаление бакета;
- перезапись объекта, если версионирование выключено (иначе перезапись
  фактически уничтожает предыдущее содержимое).

Разрешается: чтение, скачивание, создание новой версии при включённом
версионировании, создание папок-маркеров.

### 3.2. Модель данных

В `bucket_settings` добавляются поля:

```sql
ALTER TABLE bucket_settings
    ADD COLUMN object_lock_enabled boolean NOT NULL DEFAULT false,
    ADD COLUMN object_lock_mode    varchar(16) NOT NULL DEFAULT 'None';
```

`object_lock_mode`:

| Значение | Смысл |
|---|---|
| `None` | блокировка не запрошена |
| `Provider` | включён настоящий S3 Object Lock, факт подтверждён чтением конфигурации |
| `Service` | провайдер не поддерживает S3 Object Lock, включена сервисная защита |

`object_lock_enabled` — денормализованный флаг для быстрых проверок при
удалении. Он всегда согласован с `object_lock_mode`: `None` → false,
`Provider`/`Service` → true.

Существующие строки получают `false` / `None`. S3 Object Lock (`Provider`)
нельзя снять после создания — это поведение провайдера. Сервисную защиту
(`Service`) можно снять только явным действием
`PATCH /api/admin/buckets/{bucket}` с `objectLockEnabled = false`; операция
пишется в аудит. Это осознанный компромисс: иначе бакет с сервисной защитой
невозможно было бы удалить даже администратору.

### 3.3. Создание бакета

Порядок в `StorageAdminService.CreateBucketAsync`:

1. Проверить имя и квоту.
2. Если `ObjectLockEnabled = false` — создать бакет как раньше,
   `object_lock_mode = None`.
3. Если `ObjectLockEnabled = true`:
   1. Прочитать `object-lock` из реестра возможностей.
   2. Если возможность `true` — создать бакет с
      `ObjectLockEnabledForBucket = true`, затем прочитать
      `GetObjectLockConfigurationAsync` и проверить, что блокировка реально
      включена.
      - Включена → `object_lock_mode = Provider`.
      - Не включена → пометить `object-lock` как `learned = false`,
        откатить бакет и создать его заново без S3-блокировки, но с
        `object_lock_mode = Service`. В аудит пишется причина.
   3. Если возможность `false` — создать бакет без S3-блокировки и сразу
      записать `object_lock_mode = Service`.
4. Если выбран `Provider` или `Service`, версионирование обязательно:
   `versioningEnabled = true`. Если провайдер не умеет версионирование,
   создание завершается ошибкой `501` с понятным `detail`; сервисная защита
   без версионирования не имеет смысла, потому что перезапись уничтожает
   предыдущую версию.
5. Сохранить `BucketSettings` с режимом блокировки.

Откат бакета при неудачной проверке выполняется тем же механизмом, что уже
используется для версионирования: `DeleteBucketAsync` + запись в аудит.

### 3.4. Проверка при удалении

Перед удалением сервис читает `BucketSettings`:

- `DeleteObjectAsync` — если `object_lock_enabled = true`, выбросить
  `ObjectLockedException`.
- `DeleteVersionAsync` — то же.
- `DeleteBucketAsync` — то же.
- `UploadObjectAsync` — если объект уже существует, `object_lock_enabled = true`
  и версионирование выключено, выбросить `ObjectLockedException`.

`ObjectLockedException` маппится в `409 Conflict` с расширениями:

```json
{
  "title": "Object is protected from deletion",
  "status": 409,
  "detail": "Object Lock is enabled for bucket '...'; deletion through the API is forbidden.",
  "code": "OBJECT_LOCKED",
  "objectLockMode": "Service"
}
```

### 3.5. Что сервисная защита НЕ делает

Это важно зафиксировать и в UI, и в документации:

- не является S3 Object Lock;
- не поддерживает retention-сроки, legal hold, governance/compliance-режимы;
- не блокирует удаление на уровне отдельной версии по сроку;
- не защищает от прямого доступа в S3: если порт S3 опубликован наружу или
  появится другой клиент с кредами, он сможет удалить объект;
- не защищает от lifecycle-правил провайдера, если они когда-нибудь будут
  включены в обход сервиса.

Поэтому S3 должен оставаться изолированным (текущий `docker-compose.api.yml`
не публикует порт Swift). В UI режим `Service` подписывается как
«Защита от удаления на уровне сервиса», а не «Object Lock».

### 3.6. UI

- Создание бакета:
  - `objectLock = true` → чекбокс «Object Lock» с пояснением
    «Будет включён S3 Object Lock».
  - `objectLock = false` → чекбокс «Защита от удаления» с пояснением
    «Провайдер не поддерживает S3 Object Lock; защита будет работать на
    уровне сервиса».
  - В обоих случаях версионирование включается автоматически.
- Настройки бакета, вкладка «Безопасность»:
  - `Provider` → «S3 Object Lock: Включено».
  - `Service` → «Защита от удаления: Включена (уровень сервиса)» и пояснение
    об ограничениях.
  - `None` → «Выключено».
- Карточка объекта:
  - при `object_lock_enabled = true` кнопка «Удалить объект» остаётся видимой,
    но при нажатии показывается понятная ошибка `OBJECT_LOCKED`;
  - в карточке отображается бейдж «Защищён от удаления»;
  - для режима `Service` в настройках доступна кнопка «Снять защиту от
    удаления» с подтверждением; для `Provider` её нет.

## 4. API и контракты

### 4.1. Новые и изменённые эндпоинты

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/admin/capabilities` | реестр возможностей провайдера |
| `DELETE` | `/api/admin/buckets/{bucket}` | удаление пустого бакета (новая операция, см. отчёт 3.11) |
| `PATCH` | `/api/admin/buckets/{bucket}` | снятие сервисной защиты: `{"objectLockEnabled": false}` |

`BucketSecurityResponse` расширяется полем `objectLockMode`:

```json
{
  "objectLockEnabled": true,
  "objectLockMode": "Service",
  "encryption": null
}
```

Поле `objectLockEnabled` остаётся для обратной совместимости и равно
`objectLockMode != "None"`.

### 4.2. Коды ошибок

| Код | HTTP | Когда |
|---|---|---|
| `CAPABILITY_NOT_SUPPORTED` | 501 | провайдер не поддерживает операцию |
| `OBJECT_LOCKED` | 409 | удаление/перезапись защищённого объекта или бакета |
| `BUCKET_NOT_EMPTY` | 409 | удаление непустого бакета |

`ProblemDetails.Extensions` получает `code` и, где применимо, `capability`.
Фронтенд маппит `code` в русский текст, а `detail` показывает как пояснение.

## 5. Миграции и совместимость

1. EF Core-миграция добавляет `storage_capabilities` и два поля в
   `bucket_settings`.
2. При старте `Database:AutoMigrate = true` применяет миграцию; в production
   миграция применяется штатным способом.
3. `StorageCapabilitySeeder` заполняет таблицу из
   `S3:Capabilities:*`, если запись отсутствует.
4. Старые клиенты, не знающие `objectLockMode`, продолжают работать:
   `objectLockEnabled` сохранён.
5. Значения по умолчанию для неизвестного провайдера — `true` (кроме явно
   выключенных в конфиге), чтобы не спрятать рабочие функции.

## 6. Конфигурация

```json
{
  "S3": {
    "Capabilities": {
      "Versioning": true,
      "ObjectTags": false,
      "Lifecycle": false,
      "BucketPolicy": false,
      "ObjectLock": false
    }
  }
}
```

Для Swift-профиля (`docker-compose.api.yml`, `appsettings.Development.json`)
значения соответствуют таблице из раздела 1. Для MinIO все флаги можно
оставить `true`.

## 7. Тестирование

Backend:

- `CreateBucketAsync` с `ObjectLockEnabled=true` и `object-lock=false`
  создаёт бакет с `Service` и не вызывает S3 Object Lock.
- `CreateBucketAsync` с `object-lock=true`, но фактическим false — откатывает
  бакет, помечает возможность как `learned=false` и создаёт с `Service`.
- `DeleteObjectAsync` / `DeleteVersionAsync` / `DeleteBucketAsync` при
  `object_lock_enabled=true` возвращают `ObjectLockedException`.
- `UploadObjectAsync` при блокировке и выключенном версионировании
  возвращает `ObjectLockedException`.
- `StorageCapabilityStore` сохраняет и читает значения, обучение по 501
  обновляет `source=learned`.
- `GET /api/admin/capabilities` отдаёт согласованный контракт.

Frontend:

- при `objectLock=false` чекбокс подписан «Защита от удаления» и создаёт
  бакет с `objectLockEnabled=true`;
- при `lifecycle=false` кнопка добавления правила скрыта;
- при `objectTags=false` кнопка редактирования тегов скрыта;
- при `bucketPolicy=false` форма смены режима доступа скрыта;
- `OBJECT_LOCKED` показывает русское сообщение и не врёт про успех.

## 8. Статус реализации

Реализовано и проверено вживую на Swift s3api:

- `GET /api/admin/capabilities` возвращает `versioning=true`,
  `objectTags=false`, `lifecycle=false`, `bucketPolicy=false`,
  `objectLock=false`.
- Создание бакета с `objectLockEnabled=true` даёт
  `security.objectLockMode = "Service"`; удаление объекта и бакета отвечает
  `409 OBJECT_LOCKED`.
- `PATCH /api/admin/buckets/{bucket}` с `{"objectLockEnabled": false}` снимает
  сервисную защиту; после этого удаление работает.
- `DELETE /api/admin/buckets/{bucket}` удаляет пустой бакет; непустой отвечает
  `409 BUCKET_NOT_EMPTY`.
- UI скрывает Lifecycle, теги и смену режима доступа, когда провайдер их не
  поддерживает; показывает «Защита от удаления (уровень сервиса)» и бейдж
  «Защищён от удаления».
- Сортировка объектов клиентская в пределах страницы; реестр бакетов
  сортируется на сервере с направлением; активна ровно одна сортировка.
- Колонка «Версия» убрана из списка объектов, версия остаётся в карточке и
  истории версий.
- Missing-объект не запрашивает теги; действия недоступны до загрузки
  метаданных.
- Журнал операций получил фильтры по дате и ресурсу, локализованные операции и
  результаты.
- Даты Swift `2009-02-03` трактуются как отсутствие данных.

## 9. Ограничения и открытые вопросы

- Сервисная защита не заменяет S3 Object Lock; это осознанное решение.
- Если в будущем появится несколько S3-провайдеров, `storage_capabilities`
  нужно расширить ключом провайдера.
- Ручное управление возможностями через UI пока не делаем; источник —
  конфиг + обучение по 501.
- Удаление бакета требует пустого бакета; для бакетов с версиями сначала
  нужно удалить версии. Это соответствует поведению S3 и защищает от
  случайной потери данных.
