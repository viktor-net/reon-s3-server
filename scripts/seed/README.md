# Демо-данные ИС РЕОН

Скрипты наполняют стенд Reon S3 так, как это делал бы прикладной контур
**ИС РЕОН** — информационной системы Реестра единых объектов недвижимости
Москвы: реестровые дела, выписки, технические планы, фотофиксация,
пространственные слои и выгрузки для смежных систем.

## Что такое ИС РЕОН

По открытым источникам ИС РЕОН — государственная информационная система
Москвы, которая ведёт единый учёт объектов недвижимости и объединяет
информационные ресурсы города:

- земельные участки, здания, сооружения, помещения и объекты незавершённого
  строительства;
- адресный реестр зданий и сооружений и технические характеристики
  МосгорБТИ;
- цифровые топографические планы и картографический фон Мосгоргеотреста;
- сведения о собственности города (ИАС «Недвижимость-2»);
- градостроительные регламенты и линии регулирования Москомархитектуры;
- ЕГРН/ЕГРП Росреестра и данные Казначейства для прогноза доходов.

Прикладные задачи, которые решала система:

- инвентаризация и учёт состояния земель и расположенных на них объектов;
- контроль использования территории, выявление бесхозяйных объектов и
  самовольных построек;
- подготовка связанных данных о земельных участках для кадастрового учёта
  и изготовления кадастровых планов;
- прогнозирование налоговых и неналоговых доходов бюджета;
- защита имущественных интересов города;
- мониторинг территории с фотодокументированием (сравнение фотофиксаций
  объектов в разное время, контроль целевого использования участков).

Объекты в системе идентифицируются уникальными номерами (УНО — переходные
ключи), которые связывают записи разных ведомств. Доступ к данным — через
картографический интерфейс (PrimeGIS/ArcGIS), в том числе на интерактивных
столах и 3D-моделях.

запуск `seed` вернёт строки в исходные статусы.

### Бакеты административного фасада

| Бакет | Квота | Содержимое |
|---|---|---|
| `registry-cases` | 2 ГиБ | реестровые дела: папки `77-01-0001001-1234/` и `77-01-0001002-5678/`, выписка, техплан, акт, кадастровый план, схема |

Квоты пишутся в `bucket_settings`, режим доступа остаётся `Private`: Swift
s3api не поддерживает bucket policy и версионирование, поэтому `PublicRead`
дал бы рассинхрон с S3.

В `audit_events` добавляются 18 записей с действиями фасада и базового API
(`bucket.create`, `object.upload`, `file.upload`, `upload.complete`,
`object.presign` и т. д.) и ресурсами из реестровых дел.

## Чем файлы являются на самом деле

Набор не содержит «заглушек-нулей»: каждый файл — валидный файл своего
формата.

| Формат | Как сделан |
|---|---|
| DOCX | настоящий OOXML-пакет (zip + `word/document.xml`), открывается в Word и LibreOffice, кириллица внутри |
| PDF | векторный PDF с текстом и графикой; подписи латиницей и цифрами, потому что в контейнере Swift нет TTF-шрифта с кириллицей |
| PNG | процедурные изображения 512×384: фотофиксация здания и ортофото квартала, с шумом съёмки |
| SVG | схема участка с кириллическими подписями |
| CSV / GeoJSON / XML / JSONL | реестр, пространственный слой, обмен с ЕГРН, журнал мониторинга |
| ZIP | настоящий архив с CSV, GeoJSON и манифестом |
| GZ | настоящий gzip с текстом выгрузки |

Все генераторы детерминированы: одинаковый набор байтов при каждом запуске,
поэтому SHA-256 в Postgres и в S3 совпадают.

## Порядок записи

Скрипт повторяет раздел «Порядок записи» из `README.md` сервиса, а не пишет
строки «напрямую в обход»:

1. план: детерминированные `fileId` (uuid5), ключи `files/{fileId без дефисов}{ext}`,
   размер и SHA-256 содержимого;
2. `INSERT` строк `files` в статусе `Pending`;
3. `PutObject` в S3 с metadata `reon-file-id` и `reon-sha256`;
4. `UPDATE` строк в `Ready` с `etag` и `s3_version_id`, которые вернул S3.

Идентификаторы и содержимое детерминированные, поэтому повторный запуск
обновляет те же строки и объекты, а не создаёт дубликаты.

## Запуск

Стенд должен быть поднят (`docker compose ps`: `postgres` и `swift` в статусе
`running`/`healthy`).

```bash
# всё: файловый домен, бакеты фасада, квоты, журнал
bash scripts/seed/seed.sh

# только files в Postgres и объекты в бакете приложения
bash scripts/seed/seed.sh files

# только бакеты административного фасада, их квоты и audit_events
bash scripts/seed/seed.sh admin
```

Windows (PowerShell 7+):

```powershell
pwsh -File scripts/seed/seed.ps1
pwsh -File scripts/seed/seed.ps1 files
pwsh -File scripts/seed/clean.ps1
```

PowerShell-версия самодостаточна: bash не нужен, вся оркестрация выполняется
через `docker compose exec`. Скрипты `seed.sh` / `clean.sh` — для Linux, macOS
и CI.

Если политика выполнения запрещает локальные скрипты:

```powershell
pwsh -ExecutionPolicy Bypass -File scripts/seed/seed.ps1
```

Скрипт ищет `docker-compose.yml` в текущем каталоге и в корне репозитория.
Если стенд лежит в другом месте:

```bash
SEED_COMPOSE_DIR=/path/to/stand bash scripts/seed/seed.sh
```

## Проверка

```bash
curl 'http://localhost:8090/api/files?pageSize=5'
curl 'http://localhost:8090/api/admin/overview'
curl 'http://localhost:8090/api/admin/audit?pageSize=5'

# скачать любой Ready-файл по fileId из списка
curl -OJ 'http://localhost:8090/api/files/{fileId}'
```

Ожидаемо: 16 файлов `Ready` и по одному в остальных статусах,
`/api/admin/overview` показывает 4 бакета (`exports`, `object-media`,
`registry-cases`, `reon-files`), журнал — записи из сида.

## Как это устроено

- `seed.sh` / `clean.sh` (bash) и `seed.ps1` / `clean.ps1` (PowerShell 7+) —
  оркестраторы: находят стенд, кладут `seed_data.py` в контейнер Swift и
  связывают вызовы `python3` и `psql` через `docker compose exec`.
- `seed_data.py` — один файл на все режимы: `manifest`, `upload`,
  `sql-pending`, `sql-ready`, `sql-statuses`, `sql-admin`, `sql-clean`,
  `clean-s3`. В нём же генераторы DOCX, PDF, PNG, ZIP и GZ.
- Он выполняется внутри контейнера Swift, потому что там есть `boto3`;
  SQL печатается в stdout и подаётся в `psql` контейнера Postgres.

## Ограничения

- Все кадастровые номера, адреса, УНО и организации вымышленные.
- PDF без кириллицы: в образе Swift нет TTF-шрифта, а стандартные шрифты PDF
  её не содержат. Текстовые документы с кириллицей — DOCX.
- Фотофиксация и ортофото процедурные, а не реальные снимки.
- Сид не создаёт строки `multipart_uploads`: незавершённые сессии чистятся
  фоновым сервисом, и держать их в демо-данных бессмысленно.
- `bucket_settings.access_mode` не переключается в `PublicRead`: Swift s3api
  не поддерживает bucket policy.
- Демо-бакеты удаляются `clean` только если опустели; объекты, добавленные
  руками, останутся вместе с бакетом.
- Скрипты пишут напрямую в Postgres и S3, минуя API. Это допустимо только для
  dev-стенда: в рабочем контуре писать в бакет должен только сервис.
